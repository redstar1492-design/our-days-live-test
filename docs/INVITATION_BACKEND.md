# dump — 실제 계정 초대 연결 준비

기준일: 2026-10-09 · 현재 구현: 단독 HTML v20, 초대 미리보기

이 문서는 서버가 준비된 후 구현할 계약입니다. 실제 서버 프로젝트, 인증, 초대 API 또는 두 기기 연결을 구축했다는 뜻이 아닙니다. 현재 HTML은 링크로 초대 화면을 미리 보여주며 기록은 각 브라우저에 저장합니다.

## 현재 링크와 실제 초대 토큰의 구분

v20의 `#dump-invite=` 링크는 클라이언트에서 만든 **표시용 미리보기**입니다. 버전·초대한 사람의 표시 이름·무작위 식별자만 포함합니다. 서버가 발급하거나 서명하지 않았고 만료·소유권·수락 여부를 증명하지 않습니다. 실제 계정 초대 토큰이나 인증 정보로 재사용하지 않습니다.

실제 서비스에서는 로그인한 발신자의 요청에 대해 서버가 추측하기 어려운 일회성 토큰을 발급합니다. 원문 토큰은 초대 URL에만 전달하고 DB에는 안전한 해시와 발신자·만료 시각·상태를 저장하는 방식으로 구현합니다. 상대의 이름과 사진은 수신자가 자기 계정에서 설정하며 발신자가 대신 등록하지 않습니다.

## 환경 설정

준비용 예시는 [`source/v20/server/config.example.json`](../source/v20/server/config.example.json)입니다. URL과 공개 키는 빈 값이며 이를 채우는 것만으로 현재 HTML이 서버에 연결되지 않습니다.

기존 [`next-app/lib/supabase/client.ts`](../next-app/lib/supabase/client.ts)는 `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`를 읽는 코드입니다. 새 프로젝트의 publishable key를 사용할 때는 서버 앱의 설정명과 클라이언트 코드 매핑을 먼저 맞춥니다. 이번 HTML 변경에서 기존 서버 앱 코드를 수정하거나 실제 설정을 검증하지 않았습니다.

- 브라우저에는 프로젝트 URL과 공개 publishable key만 전달합니다.
- 서버 전용 비밀 키·service role key는 HTML, 공개 JSON, GitHub 저장소에 넣지 않습니다.
- 공개 키 자체가 권한 검증을 대신하지 않습니다. 로그인과 데이터별 서버 권한을 구현합니다.
- 개발·스테이징·운영 URL과 인증 redirect 허용 주소를 분리해 확인합니다.

## 제안 API 계약

경로와 필드명은 다음 서버 구현을 위한 제안이며 현재 배포된 endpoint가 아닙니다. 모든 생성·취소·수락 요청은 인증된 사용자로 처리하고 서버에서 재검증합니다.

### 초대 생성 — `POST /api/invitations`

요청: `{ "idempotencyKey": "클라이언트가 생성한 요청 ID" }`

서버는 로그인 상태, 기존 활성 커플 연결, 발신자 초대 권한을 확인합니다. 유효한 초대가 있으면 정책에 따라 재사용하거나 기존 초대를 취소하고 새 토큰을 발급합니다. 만료 시각은 서버 기준입니다.

응답 예시:

```json
{
  "invitationId": "server-generated-id",
  "inviteUrl": "https://서비스주소/invite/opaque-one-time-token",
  "expiresAt": "서버 ISO 시각",
  "status": "pending"
}
```

응답에는 다른 사람의 기록, 이메일, 사진 원문을 넣지 않습니다. 같은 idempotencyKey 재요청은 중복 초대 생성을 방지합니다.

### 초대 취소 — `POST /api/invitations/:id/revoke`

발신자만 취소할 수 있습니다. 서버는 소유권과 pending 상태를 확인하고 취소 시각을 저장합니다. 이미 취소된 요청은 같은 결과로 응답하며 수락된 연결을 초대 취소로 해제하지 않습니다. 연결 해제는 별도 동작과 정책을 둡니다.

### 초대 확인 — `GET /api/invitations/preview?token=…`

토큰 유효성·만료·취소·수락 상태를 확인해 최소한의 표시 이름만 반환합니다. 기록 조회 권한을 주지 않습니다. 응답과 로그에 토큰 원문을 불필요하게 남기지 않습니다. 이 확인만으로 커플 연결을 만들지 않습니다.

### 초대 수락 — `POST /api/invitations/accept`

요청: `{ "token": "서버 발급 토큰", "idempotencyKey": "요청 ID" }`

수신자가 자신의 계정으로 로그인하고 이름·사진을 설정한 뒤 수락합니다. 서버는 만료·취소·이미 사용된 토큰·자기 초대·기존 연결·구성원 수 제한을 모두 검증합니다.

다음 변경은 **하나의 트랜잭션**으로 처리합니다.

1. 초대 행을 잠그고 pending 상태와 만료 시각을 확인합니다.
2. 발신자와 수신자가 현재 다른 활성 연결에 속하지 않는지 확인합니다.
3. 커플과 정확히 두 구성원 관계를 생성합니다. 구성원 수는 서버/DB 제약으로 제한합니다.
4. 초대를 accepted로 기록하고 재수락을 막습니다.
5. 성공한 coupleId와 수신자의 구성원 식별자만 반환합니다.

동시 수락·중복 요청으로 세 번째 구성원이 추가되거나 여러 커플이 생기지 않도록 DB 고유 제약·잠금·트랜잭션을 사용합니다. 실패는 전체 롤백합니다. 같은 사용자의 재시도는 이미 완료된 자신의 결과를 반환할 수 있으나 다른 사용자의 재사용은 거부합니다.

## 공유 데이터와 권한

기록에는 작성자의 서버 userId와 coupleId를 별도로 저장합니다. 상대가 같이하기를 눌러도 작성자 ID는 바뀌지 않습니다. 연결 전 자기 기록을 가져올 때는 사용자 확인 후 이전 여부를 선택하도록 하고 자동 공개하지 않습니다.

DB 및 사진 저장소에는 커플 구성원 검증 정책(RLS 등)을 적용합니다. 조회·삽입·수정·삭제 각각에서 요청 사용자가 활성 구성원인지 확인하고 작성자 제한도 서버에서 판단합니다. 프런트엔드에서 버튼을 숨기는 것으로 서버 권한을 대체하지 않습니다. 초대 테이블·토큰 해시는 수신자에게 직접 조회시키지 않습니다.

## 서버 연결 후 필수 검수

- 실제 두 기기에서 초대 생성 → 수신자 가입 → 자기 프로필 → 수락 → 양쪽 연결 표시
- 취소·만료·재발급·오류 링크·자기 수락·이미 연결된 계정 처리
- 동시 수락과 재시도로 구성원이 두 명을 넘지 않는지 검증
- 다른 커플의 기록과 사진에 대한 직접 API 요청 차단
- 연결 전 개인 기록의 이전 동의와 중복 방지
- 초대/연결 실패 시 기존 기록과 프로필 보존
- 연결 해제 후 기록·사진·알림 접근 정책

실제 서버 프로젝트가 생성되면 이 문서를 구현된 계약과 검수 결과로 갱신합니다.
